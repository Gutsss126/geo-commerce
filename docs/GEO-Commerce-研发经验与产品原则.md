# GEO Commerce 研发经验与产品原则

这份文档沉淀 GEO Commerce 从 FanCrafti 接入、GA4 诊断、GEO Audit 2.0 到工作台体验优化过程中的可复用经验。它不是功能说明书，而是后续继续研发、创建 skill、交给 sub-agent 或新团队成员时的判断框架。

## 1. 产品第一性原则

GEO Commerce 的核心不是“给网站打分”，而是帮助独立站回答三个问题：

1. AI 和搜索系统能不能准确理解这个站点卖什么、适合谁、为什么可信。
2. 用户是否真的访问、点击、加购、结账，而不是只让页面结构更漂亮。
3. 优化动作是否可以被复查、被解释、被验证。

因此，任何新功能都必须服务这条链路：

`可理解 -> 可访问 -> 可行动 -> 可验证`

如果一个功能只增加信息量，但不能帮助用户更快判断下一步，它应该被折叠、后置，或暂缓。

## 2. GEO、SEO、GA4 的关系

SEO 解决的是搜索引擎能不能发现、抓取、理解页面基础内容。

GEO 解决的是 AI 和搜索系统能不能把品牌、商品、场景、可信信息和用户问题对应起来。

GA4 解决的是优化之后有没有真实行为反馈，例如访问、点击、参与、加购、结账。

三者不能互相替代：

- 没有 SEO 基础，GEO 容易变成空中楼阁。
- 没有 GEO 语义，AI 很难知道应该在什么问题里推荐你。
- 没有 GA4 验证，优化很容易变成“看起来更完整”，但不知道是否有效。

## 3. 页面体验原则

用户多数时候在乎“检查过程是否可信”，甚至超过最终分数。因此页面应优先展示：

1. 本次检查看了哪里。
2. 哪些证据缺失。
3. 当前最重要的下一步。
4. 做完后怎么验证。

默认不要把全部诊断摊开。推荐结构：

- 首屏：当前状态、当前焦点、下一步任务。
- 中段：任务中心和完成后复查。
- 后段：效果追踪和复查步骤。
- 末尾：详细诊断，默认折叠。

页面不是报告堆叠，而是工作台。

## 4. 任务中心原则

任务中心应避免变成另一个长报告。每个任务默认只展示：

- 问题是什么。
- 为什么重要。
- 完成后怎么复查。

目标、动作、验证、来源、影响、可复制内容应默认折叠。

任务优先级建议：

1. 必须做：影响基础收录、站点理解、GA4 验证闭环。
2. 建议做：提升商品语义、信任信息、FAQ、Schema。
3. 观察中：需要等 GA4、Search Console 或下一轮 audit 再判断。

好任务不是“更多建议”，而是“减少用户判断成本”。

## 5. 验证闭环原则

GEO 优化不能只用分数证明有效。更可靠的验证维度是：

- 基础有效：sitemap、robots、canonical、页面可访问、Schema 正常。
- 理解有效：品牌、商品、目标用户、使用场景、信任信息能被清楚提取。
- 流量有效：GA4 能看到页面浏览、参与、点击、加购或结账事件。
- 商业有效：订单、结账、购买归因能和页面或活动连接。
- 时间有效：不要要求实时证明长期 SEO/GEO 效果，至少观察 7/14/28 天窗口。

工具里应该明确告诉用户：

- 现在能验证什么。
- 现在还不能验证什么。
- 什么时候再看。

## 6. 自动化边界

优先自动化这些事情：

- 检查配置是否正确。
- 发现证据缺口。
- 推荐下一步任务。
- 生成可复制文案或代码片段。
- 提醒用户复查 GA4 或重新运行 Audit。

谨慎自动化这些事情：

- 自动修改用户线上网站。
- 自动判断收入增长归因。
- 自动批量改 SEO/GEO 内容。
- 过早加入复杂权限、团队、工作流系统。

原则：先帮用户少找、少猜、少记；不要替用户做不可逆或高风险决定。

## 7. 研发流程原则

每次改动尽量小步推进：

1. 先明确用户痛点。
2. 写一个能保护行为的测试。
3. 做最小实现。
4. 跑相关测试和构建。
5. 小提交。
6. 推送后让 Vercel 自动部署。

本项目常用验证：

```powershell
npx tsx scripts/test-geo-display.ts
npm run test:geo
npm run build
```

如果涉及 Prisma schema 或线上数据库字段，必须确认：

- 本地 schema 已更新。
- 线上数据库已 `prisma db push` 或完成迁移。
- Vercel 环境变量和数据库指向一致。

曾经出现过的线上错误：代码已部署但数据库缺少字段，例如 `Site.landingPath`。这类问题不是前端问题，而是 schema 与生产数据库不同步。

## 8. GA4 接入经验

GA4 集成要区分三个 ID：

- Measurement ID：形如 `G-XXXXXXXXXX`，用于页面埋点。
- Data Stream ID：纯数字，表示数据流。
- Property ID：纯数字，GA4 Data API 读取数据时使用。

常见问题：

- Vercel 环境变量不要写成 `GA4_MEASUREMENT_ID=G-xxx` 的完整字符串，值只能是 `G-xxx`。
- OAuth redirect URI 必须和 Google Cloud 后台完全一致。
- GA4 新数据流可能有初始化延迟，DebugView 比普通实时面板更适合验证埋点。
- 服务账号和 OAuth 是两套读取方式，权限问题要分别排查。

经验判断：

- 浏览器 Network 里出现 `collect?v=2&tid=G-...` 只能说明请求发出。
- GA4 DebugView 出现 `page_view`、`session_start`、`user_engagement` 才能说明数据流真正进入。
- GEO 后台读取数据延迟时，先确认 GA4 自身是否已有数据。

## 9. 站点诊断扩展原则

当前从 `/tiktok/` 单页开始是正确的，因为单页更容易验证闭环。后续扩展到站点级时，优先顺序应是：

1. 首页：品牌、主营业务、目标用户。
2. 核心落地页：活动承接和转化路径。
3. 商品页：价格、库存、评价、FAQ、Schema。
4. 信任页：配送、退货、支付、安全、联系方式。
5. 机器可读文件：sitemap、robots、llms.txt。

不要一开始就追求全站大而全。先覆盖最影响“被理解和被购买”的页面。

## 10. 可复用 Skill 提炼方向

当这份文档稳定后，可以抽成一个 Codex skill：

`geo-commerce-product-builder`

触发场景：

- 用户说继续 GEO Commerce。
- 用户要优化 GEO Audit。
- 用户要接入 GA4、WordPress、WooCommerce、Vercel。
- 用户要求优先考虑易用性、验证闭环、第一性原则。

Skill 应包含的核心规则：

- 先检查项目状态和最近提交。
- 默认先做易用性和验证闭环，不堆复杂功能。
- 新功能必须回答：用户看到什么、下一步做什么、如何确认有效。
- 页面默认折叠低优先级细节。
- 每次改动小步测试、小步提交。
- 避免自动修改线上网站，除非用户明确授权。

不建议一开始把所有经验都写进 skill。Skill 应保持短，只放高频流程；详细项目知识保留在这份文档中。

## 11. 后续产品路线

推荐顺序：

1. 继续简化 `/geo-audit` 工作台信息层级。
2. 强化任务中心，让每个任务都有复查动作。
3. 完善效果追踪，把分数、GA4、页面事件合并成可理解结论。
4. 从单页诊断扩展到核心站点页面。
5. 做站点接入向导，支持别人接自己的网址。
6. 最后再考虑多用户、权限、团队共享。

判断标准始终是：用户是否更快知道该做什么，而不是系统是否展示了更多能力。
